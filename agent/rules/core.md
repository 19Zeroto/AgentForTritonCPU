# 核心开发规则

- 在修改代码前，先向用户描述清楚修改原因和修改方案。对于跨模块、构建系统、lowering 路径或运行时语义相关的改动，应说明风险点和预期验证方式。
- 保持改动聚焦，做最小范围修改，避免大范围重构。除非用户明确要求，不要顺手改格式、重排无关代码或引入新的大依赖。
- 编写、修改或运行脚本时，遵守 `agent/rules/script-writing.md` 的路径独立性和环境路径要求。
- 新建、修改 skill，或把临时/外部脚本迁移为长期 Agent 能力时，同时遵守 `agent/rules/skill-authoring.md`。
- 修改前先阅读现有实现，优先沿用仓库已有的命名、目录结构、MLIR/LLVM pass 风格和 Python 集成方式。
- 不要假设上游 Triton 行为一定适用于 CPU 后端。
- 开始修复或审查前，先确认当前分支、工作区状态、未跟踪文件和最新 commit；不要触碰无关改动、日志或结果文件。
- 不要伪造 CUDA 设备对象让 CPU 路径“看起来像 GPU”。
- 不要用放宽测试容差掩盖 lowering 或算子错误。
- 不要为单个算子失败修改全局 JIT 或 lowering，除非能证明根因属于共享路径。
- 不要在没有指标支撑时扩大性能优化范围；性能改动不得改变默认语义，除非需求明确且有指标支撑。
- 提交 Python 改动前，使用 `code-audit` 执行定向静态检查、未使用 import 清理和格式检查。
